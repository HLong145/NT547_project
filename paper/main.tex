\begin{abstract}
A transaction sent to the wrong address cannot be undone. Shao et al.\ recently
characterized such \emph{address misuse} on Ethereum and BNB Smart Chain (BSC)
and reported the losses it causes, but they analyze each chain in isolation and
propose no mitigation at signing time. We partially replicate their detection
rules on raw transaction data and match them exactly (500/500 addresses, to the
wei, in snapshot mode). We then add a \emph{cross-chain consistency} analysis
over 45{,}633 contract-misuse addresses and eight EVM networks. Most misused
contract addresses are not random: 77.2\% (BSC) and 68.1\% (Ethereum) hold no
code on the victim chain but are contracts elsewhere, and for 98.4\%--98.8\% of
those with a known timeline the foreign contract existed \emph{before} the first
transaction, so a pre-signing check could have fired. The share of addresses is
large, but the monetary loss is concentrated elsewhere (only 18.9\% and 3.1\% of
loss), which changes how a defender should prioritize. Building on these
findings we define a risk score $R(A,C)\in[0,100]$ with four components and a
MetaMask Snap that shows the score and its reasons before the user signs.

\section{Introduction}
\label{sec:intro}
On EVM chains an address is only a 20-byte string. Nothing in the protocol tells
a sender whether the address is a wallet, a contract, a contract on another
chain, or nothing at all. A transaction with function-call data sent to an
address that holds no code succeeds silently: it spends gas, moves any attached
value, and does nothing else. A transaction sent to a wallet whose private key is
public is swept by bots within moments. Because blockchains are immutable, the
user cannot recover from either mistake.

Shao et al.~\cite{shao2026lost} measure this problem systematically and call it
\emph{address misuse}. They distinguish \emph{contract-address misuse} (the user
calls an address as if it were a contract, but it has no code or the wrong code)
from \emph{EOA misuse} (the user pays an externally owned account that is
exposed, copied from a public source, or delegated by EIP-7702~\cite{eip7702} to
malicious code). Their dataset covers Ethereum and BSC and contains large
losses. Three questions remain open.

First, their study is \emph{per chain}. Yet the same 20-byte address can be a
deployed contract on one network and empty on another, because deployer, nonce
and factory salt are chain-independent. Developers who deploy a protocol on
several chains, and users who copy an address from the wrong chain's
documentation, create exactly this situation. We call the resulting class
\emph{cross-chain misalignment} and ask how much of the observed misuse it
explains.

Second, the original analysis is retrospective. A wallet that wants to prevent
the loss needs information that was available \emph{before} the transaction:
did a contract at this address already exist elsewhere when the user first
used it? Answering this requires a timeline, not a snapshot.

Third, no wallet-side defense is evaluated. Wallets show gas and a token amount;
none tells the user that the destination looks like a contract on another chain,
or that it is a known black hole.

\medskip\noindent\textbf{Research questions.}
\begin{itemize}
\item \textbf{RQ1 (replication).} Can the detection rules of Shao et al.\ be
reproduced from raw transaction data, and where do they depend on unstated
assumptions?
\item \textbf{RQ2 (cross-chain).} What share of contract-address misuse is
explained by cross-chain misalignment, how much loss does it carry, was the
foreign contract already deployed at the time of misuse, and can the address
still be claimed on the victim chain?
\item \textbf{RQ3 (mitigation).} Can a risk score computed from information
available before signing separate misuse from benign transactions at a low
false-positive rate and within a latency budget a wallet can afford?
\end{itemize}

\medskip\noindent\textbf{Contributions.}
\begin{itemize}
\item \emph{Replication.} A port of the detection rules and the symbolic
executor to a public toolchain. On 500 sampled Ethereum addresses we reproduce
the original misuse transactions and loss exactly in snapshot mode, and on 246
contracts the symbolic executor agrees with the original results on all four
flags. We document four defects in the released code
(Section~\ref{sec:replication}).
\item \emph{Cross-chain measurement.} The first address$\times$chain consistency
matrix of 45{,}633 misused contract addresses over eight networks, with root
cause (deployer, nonce, factory), timing and redeployability
(Section~\ref{sec:matrix}, Section~\ref{sec:eval-xc}).
\item \emph{Gold labels and negatives.} A codebook, two-annotator protocol with
a target Cohen's $\kappa\ge0.8$, and negative sets N1--N8 that include benign
EIP-7702 delegates and multi-chain infrastructure contracts that a naive
detector would flag (Section~\ref{sec:gold}).
\item \emph{Mitigation.} A four-component risk score $R(A,C)$ with
explanations and hard rules, and a MetaMask Snap design with a 150~ms budget
(Section~\ref{sec:design}).
\end{itemize}

\section{Background and Threat Model}
\label{sec:background}
\subsection{Accounts, code and CREATE addresses}
An EVM account is either an externally owned account (EOA), controlled by a
private key, or a contract account that holds code. We write $\code{C}{A}$ for
the code at address $A$ on chain $C$, with three states: $\emptyset$ (no code),
$\kappa$ (contract code) and $\delta$ (an EIP-7702 delegation indicator, bytecode
starting with \texttt{0xef0100}). A contract created with \texttt{CREATE} lives at
$\text{keccak}_{160}(\text{rlp}(d,n))$ for deployer $d$ and nonce $n$; with
\texttt{CREATE2} at $\text{keccak}_{160}(\texttt{0xff}\Vert d\Vert s\Vert
\text{keccak}(\mathit{init}))$. Neither formula contains a chain identifier.
Hence the same deployer using the same nonce, or the same factory with the same
salt and init code, yields the same address on every EVM chain. This property is
what makes multi-chain deployments convenient and misalignment possible.

\subsection{Address misuse}
Following~\cite{shao2026lost} we use these categories.
\begin{description}
\item[\NCD{} (No Code at Destination).] $\code{C}{A}=\emptyset$ when the user
sends a transaction that carries a function selector or otherwise only makes
sense for a contract. The transaction does not revert, so the user sees success.
\item[\PCD{} (Planted/Present Code at Destination).] $\code{C}{A}=\kappa$ but
$\kappa$ is not the contract the user meant; value is retained or forwarded.
\item[KEY.] $A$ is an EOA whose private key is public (repositories, forum
posts). Sweeper bots drain deposits within blocks.
\item[ADDR.] $A$ is a public wallet address copied from documentation or sample
code and the sender does not control it.
\item[EIP-7702.] $\code{C}{A}=\delta$ and the delegate is a sweeper or otherwise
malicious. Funds sent to the EOA are handled by the delegate's code.
\end{description}

\subsection{Taxonomy}
Our codebook refines these into six mutually exclusive types by priority
(Table~\ref{tab:taxonomy}); T4 outranks T1 and T5 outranks T6. T4 is the new
class of this paper.
\begin{table}[t]
\caption{Taxonomy of address misuse used in this work. $t_0$ is the time of the
first transaction to the address on the chain under study.}
\label{tab:taxonomy}
\centering
\begin{tabular}{@{}llp{6.9cm}@{}}
\toprule
Type & Name & Defining condition\\
\midrule
T1 & Call to empty address & \NCD{} and no contract at that address on any other
chain before $t_0$\\
T2 & Black-hole contract & Code present, receives coin, no withdrawal path

\end{tabular}

\subsection{Threat model and ethics}
We study a \emph{careless-user} threat: the user is honest and the chain is
correct, but the destination is wrong. We also consider an \emph{opportunistic
adversary} who monitors addresses (sweepers, address poisoners, anyone who can
redeploy a contract at an unclaimed address). The adversary does not break
cryptography. The defender is the wallet, which can read public chain state
before signing but cannot know the user's intent.

All measurements are passive reads of public data. We never sign or send a
transaction with a leaked key and never store private keys; the data contain only
derived addresses. Personal addresses are truncated in the text
(\texttt{0x1234\ldots abcd}). \todo{Responsible-disclosure statement: which wallet vendors and affected projects were notified, and when.}

\subsection{Rule replication}
\label{sec:replication}
We port Algorithms~1--3 of~\cite{shao2026lost} (NCD, PCD and EOA loss) to a
Windows-compatible toolchain with Etherscan API V2. We run two modes: a
\emph{snapshot} mode that uses only the first $n_{tx}$ transactions, as at the
original collection time, and a \emph{current} mode with all transactions.
While porting we found defects in the released code that change results, so we
keep an option to reproduce them (\texttt{paper\_compat}):
\begin{itemize}
\item B1: the condition \texttt{len != 10 or len != 74} is always true, so every
transaction with selector \texttt{0xffffffff} is skipped;
\item B2: the sweep detector does not stop after a match, so one deposit can be
counted more than once;
\item B3/B4: the code fetcher passes its API key as the chain parameter and the
symbolic executor uses \texttt{SIGALRM}, so neither runs as released (the latter
cannot run on Windows); we replace the timeout with a basic-block deadline;
\item the paper states \texttt{tx.gas < 30000} while the code uses
\texttt{gasUsed <= 30000}; we follow the code.
\end{itemize}
The NCD rule also relies on the explorer-provided \texttt{functionName}, which
raw data lack, and the PCD rule excludes an address that ever sent a
transaction, which is wrong for an EOA that later adopts EIP-7702.

\subsection{Cross-chain consistency matrix}
\label{sec:matrix}
Let $\mathcal{N}$ be the eight networks and $V\in\mathcal{N}$ the chain on which
an address $A$ was misused. For each $A$ we read $\code{C}{A}$ for every
$C\in\mathcal{N}$, giving the vector $M_A=(\code{C}{A})_{C\in\mathcal{N}}$.
\begin{definition}[Cross-chain labels]
$A$ is \NCDXC{} if $\code{V}{A}=\emptyset$ and $\exists C\ne V:\code{C}{A}=\kappa$.
It is \PCDXC{} if $\code{V}{A}=\kappa$ and $\exists C\ne V$ with
$\code{C}{A}=\kappa'$ where $\kappa'$ has different bytecode. Otherwise the
label is \textsf{-Other}. If the code is identical on $V$ and $C$, we do not
label it, since that is a benign multi-chain deployment (N7).
\end{definition}
For each foreign contract we record the creator, creation kind, and for
\texttt{CREATE} the deployer nonce, which we recover locally by searching
$\text{create\_address}(d,n)$ up to $n\le200{,}000$ (public RPCs do not index old
transactions on several chains, so fetching the nonce is not reliable). We then
derive two quantities.

\paragraph{Timing.} Let $t_c$ be the earliest known creation time of the foreign
contract and $t_0$ the first external transaction to $A$ on $V$. The address is
\emph{deployed\_before} if $t_c<t_0$, and \emph{deployed\_after} otherwise. This
separates T4 from T1: a deployment after $t_0$ cannot have warned anyone.

\paragraph{Redeployability.} Let $n_V$ be the current nonce of the creator on $V$
and $n_c$ the nonce used for the foreign contract. For a \texttt{CREATE}
deployment the address is \emph{claimable} if $n_V\le n_c$ (the owner can still
produce it on $V$), \emph{burned} if $n_V>n_c$, and \emph{already deployed} if
code exists. If the creator is a factory, we record whether the factory itself
exists on $V$. Claimable addresses matter twice: they give the owner a way to
close the hole, and they give an attacker holding the deployer key a way to
capture funds that users keep sending.

\subsection{Gold labels and negative sets}
\label{sec:gold}
\paragraph{Protocol.} The unit of annotation is a pair (chain, address). Two
annotators label independently with a written codebook that contains a decision
tree and hard cases; agreement is measured by Cohen's $\kappa$ with target
$\ge0.8$, followed by adjudication and codebook revision. We first run a pilot
of 50 items. The evidence presented to annotators is \emph{blinded}: every item
gets the same evidence columns for all strata, because in an earlier version a
column that was filled only for some strata let annotators infer the stratum.
The hidden key is never shown.

\paragraph{Sample and agreement.} The sampling frame is the 2{,}010 test and
out-of-time rows of our dataset, grouped into cells by author stratum, chain and
whether the frozen detector flags the address. Batch~1 labels every
author-positive address and the flagged negatives (a census) and a simple random
sample of the unflagged negative cells, 758 addresses in total; estimates use
Horvitz--Thompson weights (cell size over labelled count) and a bootstrap that
resamples within sampled cells. Of these, 200 were labelled by both annotators.
The first 50 double-labelled items served as a gate: $\kappa=0.69$ missed the
pre-registered 0.70, so we revised the codebook once (v0.6.3) and measured the
official $\kappa$ on the 200 items that had not been used for the revision:
$\kappa(\text{misuse})=0.80$ [0.69--0.90], 180/200 agreement, and
$\kappa(\text{type})=0.82$. A rule that labels mechanically from the evidence
columns agrees with the final labels only at $\kappa=0.48$, and annotator
disagreement concentrates where it fails ($\kappa=0.10$ on those 54 items), so
the labels add information beyond the columns. All 30 disagreements were
adjudicated in writing; the final set has 441 positives (T5 261, T4 137, T1 41,
T2 1, T3 1) and 317 negatives.

\paragraph{Negatives.} A detector can only be evaluated against realistic
benign cases.
\begin{itemize}
\item N1: 400 random addresses from the same public-code candidate pool that
are not flagged (200 per chain);
\item N6: five verified benign 7702 delegates (MetaMask, Coinbase, Uniswap,
eth-infinitism Simple7702Account, Ambire);
\item N7: 18 infrastructure contracts deployed at the same address on at least
six networks (CREATE2 factories, Multicall3, Permit2, Safe, EntryPoint, 1inch,
0x, Seaport);
\item N2--N5, N8 (exchange deposits, inscriptions, ordinary transactions):
\todo{build after D1.}
\end{itemize}
The negatives already reveal pitfalls. Permit2, 1inch, 0x and Seaport have
\emph{different} bytecode across chains (chain id and immutables), so a
detector must not require identical bytecode. In N1, 14 of 400 addresses (3.5\%)
currently delegate through EIP-7702, so a wallet cannot warn on every delegated
EOA.

\section{Risk Score and Wallet-Side Warning}
\label{sec:design}
\subsection{Risk score}
For destination $A$ on chain $C$ at time $t$, the score uses only information
available before $t$:
\begin{equation}
R(A,C)=100\,\bigl(w_1S_{\mathrm{bytecode}}+w_2S_{\mathrm{cross}}+w_3S_{\mathrm{osint}}+w_4S_{\mathrm{history}}\bigr),
\end{equation}
with $S_i\in[0,1]$, $w_i\ge0$ and $\sum_iw_i=1$. Using only past information is
essential: in 283 of 17{,}918 timed Ethereum cases the foreign contract appears
after the first transaction, and a score that reads today's state would
``see the future''.

\paragraph{Components.}
\begin{itemize}
\item $S_{\mathrm{bytecode}}$ examines $\code{C}{A}$: a call with data to an empty
address scores 1 (T1); a code that offline symbolic execution shows has no
withdrawal path scores 1 (T2); a known malicious delegate scores 1 (T5); a
verified benign delegate scores 0; an unknown delegate that can move funds
scores 0.5, because the ability to move funds does not distinguish a sweeper from
a smart wallet.
\item $S_{\mathrm{cross}}$ scores 1 when $\code{C}{A}=\emptyset$ and a contract
existed on another chain before $t$ (T4), 0.7 if the foreign deployment time is
unknown, 0.6 for different code on both chains, and 0 for identical code
(benign N7). A small increment applies when the address is claimable.
\item $S_{\mathrm{osint}}$ is 1 for addresses derived from a leaked key and
saturates with the number of public sources that mention the address.
\item $S_{\mathrm{history}}=1-(1-s_{\mathrm{sweep}})(1-s_{\mathrm{revert}})(1-s_{\mathrm{misuse}})$
combines the fraction of deposits swept within a few blocks, the revert rate and
earlier hits of the replicated rules from multiple senders.
\end{itemize}

\paragraph{Learning and thresholds.} We fit a logistic regression with
non-negative coefficients on the four components using a time-split, address-disjoint
train/validation/test partition, then normalize coefficients to obtain $w_i$.
The warning threshold $\tau_{\mathrm{warn}}$ is the lowest value with false
positive rate $\le1\%$ on ordinary transactions (N8) on the validation set.
Two hard rules, leaked key and known malicious delegate, warn regardless of $R$;
we report their effect separately so they do not inflate the score's apparent
quality. The learned weights are $w_{\mathrm{bytecode}}=0.522$,
$w_{\mathrm{osint}}=0.359$, $w_{\mathrm{cross}}=0.086$ and
$w_{\mathrm{history}}=0.033$, with $\tau_{\mathrm{warn}}=63.0$ and
$\tau_{\mathrm{block}}=65.7$. The threshold is fragile: an address-level
bootstrap of the validation set (only 186 ordinary-transaction negatives) gives
$\tau_{\mathrm{warn}}$ percentiles p5 25.9, p50 63.0 and p95 65.7.

\subsection{Wallet-side warning}
The warning is split into an \emph{offline} part that precomputes expensive
facts and an \emph{online} part that stays within the latency budget.
Symbolic execution takes seconds to minutes and also exhausted memory on 37 of
344 contracts at 850~MB, so it is run offline and stored in a lookup table;
unknown contracts fall back to a fast opcode scan for \texttt{CALL},
\texttt{DELEGATECALL} and \texttt{SELFDESTRUCT}. Online, the engine reads the
code at the destination on the current chain and, in parallel, on the other seven
networks with a 100~ms timeout per network; a network that times out is skipped
and listed in the explanation, and the transaction is never blocked merely
because an RPC was slow.

A MetaMask Snap uses the transaction-insight interface to call this engine
before the user signs, and shows the score, the suspected type and one-line
reasons (``this address is a contract on Ethereum, deployed 3 days earlier, but
empty on this chain''). The latency target is \SI{150}{\milli\second}. Our
measurements of public RPCs from our network give 0.9--1.3~s per call with peaks
of 8--9~s, so the target requires caching, a dedicated RPC provider and short
timeouts. \todo{Architecture figure and measured median and p95 latency.}

\section{Evaluation}
\label{sec:eval}
\subsection{Replication (RQ1)}
\paragraph{Rules.} On 500 Ethereum addresses (350 NCD, 100 PCD, 50 KEY; at most
5{,}000 transactions each) the snapshot mode reproduces the original result
\emph{to the wei}: 500 of 500 addresses and a total of 579.759~ETH. Table~\ref{tab:repl} shows that the
current mode adds little loss but changes labels over time.
\begin{table}[t]
\caption{Replication on 500 Ethereum addresses.}
\label{tab:repl}
\centering
\begin{tabular}{@{}lll@{}}
\toprule
Mode & Result & Observation\\
\midrule
Snapshot & 500/500 exact match & total 579.759 ETH\\
Current & loss $+0.02\%$ & 98 new NCD misuse tx on 20 addresses;\\
 & & 2 NCD became PCD; 24/50 KEY received 238 more tx\\
\bottomrule
\end{tabular}
\end{table}
Misuse is therefore continuing after the original collection, and NCD/PCD labels
change over time, so any dataset must carry its observation date.

\paragraph{Symbolic execution.} On 344 contracts (all EIP-7702 delegates, proxy
logic and 150 sampled misuse addresses), 307 completed within memory. On the 246
that finished within the 120~s soft deadline our results match the authors' on
all four flags (delegatecall, transfer all ETH, transfer \texttt{msg.value},
transfer input amount) at 100\%. Including timed-out contracts, agreement is
99.0--99.7\% per flag and every disagreement has the same direction: the original
reports a path and ours, stopped earlier, does not.

\paragraph{EIP-7702 delegates.} The authors' delegate flag coincides exactly with
symbolic execution: 89 of 89 delegates have a transfer path, 2 have none and 10
are unanalyzed. It is therefore not a label of maliciousness, and the benign
MetaMask delegate carries flag~1. All 17{,}326 authorizations in the dataset come
from KEY or ADDR EOAs, so there is no benign EIP-7702 EOA among the positives.

Cross-chain misalignment is the dominant pattern by \emph{count} but not by

600 random addresses on three chains had no code, ruling out spurious RPC
answers. Most addresses have code on a single other chain, mostly ETH$\leftrightarrow$BSC (13{,}223 BSC

An asymmetry appears in the top-100 NCD addresses per chain: 36 of 100 on BSC
are contracts on another chain (13\% of the loss, for example Uniswap V3
SwapRouter) but only 2 of 100 on ETH. The largest NCD on Ethereum are probably
copies from decommissioned testnets (Ropsten, Rinkeby, Kovan, Goerli), which no
live RPC can show; GitHub context is needed to confirm this.

\paragraph{Why v1 misses.} Two causes explain most false negatives. First, a pure
T1 signal (a call with data to an empty address) gives
$R=100\,w_{\mathrm{bytecode}}=62.4$, just below $\tau_{\mathrm{warn}}=63.0$, so
the learned weights suppress T1 unless another component fires. Second, the
history feature sees only the last 1{,}000 native-coin transactions before $t$,
whereas 36 of the 45 missed leaked-key addresses had already made at least two
fast withdrawals before $t$, mostly of tokens. Engine v2 therefore adds two
pre-registered rules with thresholds taken unchanged from the codebook: warn
on a call with data to an address with no code (\texttt{ncd\_call}), and warn when the
full asset history (native, internal, ERC-20/721/1155) shows at least two fast
withdrawals ($\le600$\,s, 90--102\% of the deposit, to a third party, no asset
returned) before $t$ (\texttt{sweeper\_full}). On batch~1, v2 raises recall to
0.935 at precision 0.834 (Table~\ref{tab:gold}). Of its 81 new warnings, 59 are
gold positives; 11 of the 22 false warnings are exchange deposit wallets whose
forwards look like sweeps, which a wallet could suppress with exchange labels.
Because v2 was designed on this batch, we evaluate it on a held-out batch below.

\section{Discussion and Limitations}
\label{sec:discussion}
\paragraph{Implications.} Wallets should check whether an address with no code on
the current chain is a contract on another one, and surface the result at the
first use. Because most NCD-XC cases involve only gas, the warning prevents
frequent small mistakes; large losses need history and hard rules. Project teams
that deploy on several chains should claim the same address everywhere, or burn
the nonce deliberately, instead of leaving it claimable. Explorers could mark
``this address is a contract on chain X''.

\paragraph{Limitations.}
\begin{itemize}
\item \emph{State versus time.} Code is the latest state. We use creation time to
approximate history, but cases whose code later changed are not fully resolved.
\item \emph{Coverage.} Creation data missing for OP, Base and BSC testnet make
timing a lower bound; the original ETH dataset itself is a snapshot.
\item \emph{External transactions only.} The first transaction ignores internal
transfers.
\item \emph{Rules requiring \texttt{input}.} We excluded \texttt{input} from the
BigQuery scan for cost reasons, so NCD/PCD rules are evaluated on subsets
through an explorer.
\item \emph{Label subjectivity.} Intent cannot be observed; we mitigate with a
codebook and $\kappa$, but a residual remains.
\item \emph{Scope.} Two source chains and eight networks; results may differ for
other EVM chains.
\end{itemize}

\paragraph{Ethics.} See Section~\ref{sec:background}. We publish derived
statistics and truncated addresses, not keys.

%------------------------------------------------------------------
\section{Conclusion}
\label{sec:conclusion}
We replicated the address-misuse rules exactly in snapshot mode, showed that
most misused contract addresses are empty on the victim chain but real contracts
elsewhere, and that those contracts almost always came first. This gives wallets
a signal available before signing, and gives project owners a concrete action,
claiming the address. The cross-chain class is large in count but small in value,
so a defense needs more than one signal. Future work: complete the gold set and
evaluation, add the history and OSINT features, and measure the Snap in real
conditions. \todo{Update after RQ3 results.}
